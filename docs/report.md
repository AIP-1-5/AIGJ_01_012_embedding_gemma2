## 과제 1. 카메라 연동과 기준선

**미수행.** 수신 루프 (a)/(b) 비교, 첫 프레임 지연, glass-to-glass, 재연결 시험, IP 카메라·RTSP는 하지 않았습니다.

관련해서 실제로 겪은 것만 적습니다.
- 해결할 것 5번(헤드리스 보드를 PC 브라우저로 보기)은 8~10단계 내내 이 방식으로 했습니다. 보드 모니터 없이 FastAPI MJPEG(`/stream`)를 Tailscale 주소의 노트북 브라우저로 봤습니다.
- 8·9단계 앱은 한 스레드가 `cap.read()` 다음 바로 검출하는 (a)에 가까운 구조이고(카메라 30fps, 처리 12~13fps), 10단계 `proximity_app.py`는 카메라마다 스레드가 읽고 최신 1장만 남기는 (b) 방식(`CAP_PROP_BUFFERSIZE 1`)입니다. 두 방식의 지연을 비교해 재지는 않았습니다.
- 8단계 1차에서 Ctrl+C 뒤 python이 D 상태로 멈춰 `kill -9`가 필요했습니다(카메라 스레드가 `cap.read()` 중에 프로그램이 내려가며 uvcvideo가 스트림을 끊는 단계에서 걸린 것으로 추정). 멈춤 신호를 먼저 주고 카메라를 놓는 순서로 고친 뒤 다시 생기지 않았습니다. 카메라를 뽑았다 꽂는 복구 시험은 하지 않았습니다.

### 무엇을 바꿨고 무엇이 달라졌나

- 2차에서 relabel이 COCO 물체(휴대폰)를 망가뜨렸습니다. 고쳐 주는 힘과 망가뜨리는 힘이 같은 규칙(1위면 덮어쓰기)에서 나왔기 때문입니다.
- 3차에 **"검출기 이름이 목록에 있고 1위와 0.03 안이면 그대로 둔다"(`KEEP_MARGIN`)** 를 넣었습니다. 휴대폰은 검출기 이름이 이미 1위라 그대로 남았고, 세탁기(차이 0.05)·건전지(차이 0.17)는 고쳐졌습니다.
- 결론: 교실 서비스에는 yolo11n 박스 + 조건부 재라벨, 그리고 이름이 틀려도 찾을 수 있는 텍스트 검색을 같이 둡니다. 세 방식 속도는 12~13fps로 거의 같았고, 메모리 여유(최저 1.2GB)가 작아 다른 앱과 같이 띄우지 않습니다.

### 행동 패턴: 규칙 vs 학습 모델

| 시나리오 (3회씩) | 규칙 (9-5, 최종) | GRU 행동 모델 (3차) |
| --- | --- | --- |
| 그냥 지나감 → 지나감 | 0/3 (모두 힐끗 봄) | 2/3 (1회 미검출) |

| 옆 보며 15초 서 있음 → 머무름 | 0/3 | 모델에 머무름 라벨 없음 (3회 모두 힐끗 봄) |
| **합계** | **4/12** | **7/9** (머무름 제외) |

동작 모델(검증 0.641) 혼동 행렬 (행=정답, 열=예측):

```
               arms_crossed  clap  idle  wave
arms_crossed             20     0     0    11
clap                      0    15     0    21
idle                      0     0     4    15
wave                      0     0     0    45
```

학습 모델은 규칙으로는 불가능한 **박수·팔짱을 보드에서 알아봤고**, 행동에서는 규칙이 약했던 **관심 있음**에서 이겼습니다. 다만 학습·평가가 같은 사람·같은 장소·같은 날이라 근거가 약합니다.

### 혼동 사례 분석

| # | 실제 | 판정 | 원인 분류 | 설명 |
| --- | --- | --- | --- | --- |
| 1 | 만세 | 만세↔한팔들기 0.1초 간격 깜빡임 | 창 길이 | 팔을 올리는 중 한쪽 손목만 먼저 기준선을 넘음. raw 16·37 → 다수결 0.6초로 3·5 |
| 2 | 측면 만세 | 빠짐 | 각도·가림 | 옆모습에서 반대쪽 어깨가 가려 `body()`가 판정 자체를 안 함 |
| 3 | 어깨 높이 손 흔들기 | 한팔들기 | 각도(동작 크기) | 손목 좌우 폭이 기준(어깨 너비 0.15배)보다 작음. 팔을 머리 위로 들고 크게 흔들어야만 잡힘 |
| 4 | 손 흔들기 1번 | 손흔들기 2번 | 창 길이 | 1.5초 창 안에서 방향 전환이 2번 아래로 떨어지면 한팔들기로 돌아갔다 다시 손흔들기 |
| 5 | 악수 | 1차 0회 | 각도 | 옆모습에서 어깨 너비가 작아져 "손목 거리 < 어깨 너비 × 0.5" 범위가 좁아짐(추정) |
| 6 | 그냥 지나감 | 힐끗 봄 | 추적(ID 쪼개짐) | ID가 쪼개지면 짧은 조각 하나만 정면으로 읽혀도 "가장 높은 단계"가 힐끗 봄이 됨 |
| 7 | 옆 보며 서 있음 | 관심 있음 | 추적(ID 합쳐짐) | 4-1과 4-2가 한 사람(체류 36초)으로 이어져 시도 사이 대기 시간의 정면 시간이 합쳐짐 |
| 8 | 가만히·박수 (GRU) | 손 흔들기 | 데이터(사람 1명) | 손 흔들기 과다 예측(idle 15/19, clap 21/36). 녹화 앞뒤 키보드 신호 구간이 섞인 것도 원인 후보 |

### 무엇을 바꿨고 무엇이 달라졌나

- 손 흔들기: 동작 방식(팔을 머리 위로)만 바꿔 0/3 → 5번. 원래 규칙은 큰 손 흔들기만 알아본다는 뜻입니다.
- 행동 모델: 1·2차는 한 번 지나갈 때 추적이 약 2초뿐이라 window 40(약 2.6초)을 못 채워 학습이 안 됐습니다. 3차에 **천천히 걸어 다시 녹화**하고 window 40/stride 5로 학습해 9회 중 7회가 됐습니다.

### 접근 알람과 이동 타겟

- 타겟 자동 찾기(YOLOE 후보 → EmbeddingGemma 2로 선택): "brown cardboard box", 바닥 위치 오차 0.31m. 두 시선 각도가 23도로 좁아 앞뒤(y) 오차가 컸습니다.
- 시나리오 5개(걸어옴·이탈·경계 10초·옆 지나감·옆 책상에 앉음) 모두 3/3. 경계에서 20초 서 있어도 근접 알람은 1번(히스테리시스 0.2m).
- 이동 타겟: 충돌 위험 알람이 근접 알람보다 천천히 3초, 빠르게 몇 프레임 먼저. `--ttc 3.0`에서는 보통 속도 1초 먼저(2.4m, 2.2m), 거리 ≈ 접근 속도 × TTC와 맞음.
- 헛알람: 몸을 돌리거나 앉을 때 생기는 0~1초짜리 가짜 ID가 불필요한 근접 알람을 냈습니다. 횟수를 따로 세지 않아 헛알람율은 없습니다.

### `prox` 방식 vs 정렬형 스테레오 (비교 측정은 안 함, 경험 정리)

| | `prox` 방식 (우리가 한 것) | 정렬형 스테레오 (안 함) |
| --- | --- | --- |
| 설치 | 카메라를 방의 다른 곳에 따로 둠. 기준점 줄자 실측 필요 | 평판에 나란히 고정 |
| 커버 범위 | 방 전체 평면도 | 두 카메라 앞 원뿔 |
| 약점 | 기준점 측정 품질이 그대로 오차가 됨, 카메라가 조금만 움직여도 재보정(실제로 cam0이 돌아감) | 거리 제곱으로 오차 증가, 무늬 없는 곳 측정 불가 |

### 무엇을 바꿨고 무엇이 달라졌나

- 위치 계산을 발목(1대) → 어깨 삼각측량(2대)으로 바꾸자 앉은 사람 오차가 0.64m → 0.14m.
- 카메라 높이 1.4m에서는 한 카메라 추정(어깨 1.2m 가정)이 1.26m 빗나갔습니다. 시선이 거의 수평이라 가정이 조금만 틀려도 거리가 크게 틀어지기 때문이고, 원문 권장 높이 2.2~2.5m가 필요한 이유를 확인했습니다.

## 과제 6. 응용 서비스

**미수행.** 가동 중인 서비스, MQTT 발행, systemd 유닛, 자원 계획표, 12시간 가동, 장애 시험이 없습니다.

있는 것: 10단계 접근 감지 앱(`proximity_app.py`)은 웹 화면과 `/state` JSON으로 거리·알람을 보여 줍니다. 이 HTTP 주소만 [result_format.md](result_format.md)에 적었습니다. 같은 보드에서 다른 프로젝트 서비스가 상시로 돌고 있어, 실습 앱은 메모리 제한(`MemoryMax=2500M`)을 걸고 필요할 때만 켰습니다.
